# Phase 0 Research: Academy Live Coaching (Calendly Replacement)

**Branch**: `017-live-coaching` | **Date**: 2026-09-22 | **Spec**: [spec.md](./spec.md)

Every decision below resolves a "how" the spec deliberately leaves open, or a technical question the source developer spec raised without answering. The engine-vs-Cal.com fork is not re-litigated here — the user already decided (see plan.md's Summary) to keep extending 013's existing custom implementation.

## 1. Zoom integration: Server-to-Server OAuth, per-coach connection, plain `fetch`

**Decision**: Each Coach connects their own Zoom account via a Server-to-Server OAuth app (Zoom's current recommended pattern — the older JWT app type is deprecated). No Zoom SDK is added as a dependency; `src/lib/booking/zoom.ts` calls Zoom's REST API directly with `fetch`, exactly mirroring how Ask a Coach wraps Mux's API (`@mux/mux-node` is a real SDK Mux publishes and maintains; Zoom's meeting-management surface has no equivalent actively-maintained Node package, only a video *rendering* SDK for embedding Zoom's UI, which is not what this feature needs).

**Rationale**: Per-coach connections (rather than one company account creating meetings with each Coach as host) avoid concentrating Zoom's per-user daily meeting-create/update rate limit across the entire coaching staff on a single account — a real risk the source spec explicitly flags (100–400 calls/day depending on account tier, unconfirmed exact current limit). A meeting-creation failure (rate limit, expired token, Zoom outage) is caught and recorded per FR-032/Edge Cases without blocking the booking; a lightweight retry (re-attempt on the next booking-detail view, or a short backoff queue) picks it up rather than the Student being permanently left without a link.

**Alternatives considered**: One shared company Zoom account (the source spec's second listed option) was rejected as the default — it's simpler to set up (one OAuth connection, not N), but caps the whole coaching staff's combined meeting creation under one account's rate limit and requires every Coach to trust a shared credential. It remains a valid Admin-configurable choice, not removed from the design (data-model.md's `external_calendar_connections`-adjacent Zoom connection record is per-Coach by default but not schema-locked to be), matching the spec's Assumptions note that this defaults per-coach without ruling out the alternative later.

## 2. Calendar sync: three distinct client libraries behind one shared interface

**Decision**: `src/lib/booking/calendar-sync/index.ts` defines a small shared interface (`connect`, `listBusyBlocks(range)`, `createBookingEvent(booking)`, `renew`/`poll`) that three provider-specific modules implement:
- **Google**: `googleapis` (official), OAuth 2.0, Calendar API push channels (`watch()`) for near-real-time conflict updates.
- **Microsoft 365/Outlook**: `@microsoft/microsoft-graph-client` + `@azure/msal-node`, Graph API webhook subscriptions (Microsoft's equivalent of push channels).
- **Apple iCloud**: `tsdav` (a maintained CalDAV client), authenticated with an app-specific password (iCloud has no OAuth for third-party calendar apps) — no push support, so `poll-icloud/route.ts` polls on a fixed interval (research item #3's renewal job doubles as the polling trigger for this provider).

**Rationale**: The three providers have genuinely incompatible protocols (Google/Microsoft: REST + OAuth + push; iCloud: CalDAV + app password + poll-only) — a single unified client library doesn't exist that covers all three well, so a shared *interface* with three small implementations is the right level of abstraction, not a shared *client*. This keeps each provider's quirks contained to one file, and the booking-availability code (`availability.ts`) only ever calls the shared interface, never a provider SDK directly.

**Alternatives considered**: A unified calendar API service (e.g. Nylas, Cronofy) was considered — it collapses all three providers behind one API and one webhook format, trading three integrations for one paid third-party dependency. Rejected for now to avoid adding an external paid vendor before the coaching team's actual calendar-provider mix is known in practice; the shared-interface design here means swapping in a unified provider later is a contained change (one new `calendar-sync/*.ts` implementation) if it turns out to be worth it.

## 3. Renewal/polling job and encrypted OAuth token storage

**Decision**: `external_calendar_connections` stores each connection's OAuth access/refresh tokens (Google, Microsoft) or CalDAV app-specific password (iCloud), encrypted at rest using the same symmetric-encryption helper pattern already used elsewhere in this codebase for sensitive stored values (application-level AES via a server-only secret, not pgcrypto — keeping encryption/decryption in application code rather than the database keeps the key out of connection strings and query logs). `calendar_sync_state` tracks each connection's push-channel/subscription expiry; `/api/booking/calendar-sync/renew` (cron-triggered, same external-scheduler pattern 013 already established for `send-reminders`) renews any channel expiring within 24 hours and flags a connection "needs reconnect" if a renewal call itself fails (expired/revoked refresh token) rather than silently letting stale availability be trusted (FR-012, Edge Cases).

**Rationale**: Google push channels expire after at most 7 days and Microsoft Graph subscriptions need renewal too (source spec, citing Truto's 2026 guide) — without an active renewal job, sync silently goes stale days after a Coach connects, which is worse than no sync at all because a Coach would believe conflicts are still being caught. Reusing 013's existing cron-Route-Handler pattern (rather than introducing a real job queue/worker process) keeps this consistent with the only background-job mechanism this codebase has ever used.

**Alternatives considered**: A dedicated job queue (BullMQ/similar, backed by Redis) was considered for retry/backoff sophistication across Zoom, calendar renewal, and credit calls. Rejected — no queue infrastructure (Redis or otherwise) exists anywhere in this repo today, and 013's simple pattern (an externally-triggered Route Handler that scans for due work each run) has already proven sufficient for reminders; introducing a new piece of infrastructure for this feature alone is a bigger architectural change than the feature needs, and can be revisited if reminder/renewal/retry volume ever actually strains the cron-scan approach.

## 4. DST-safe availability storage

**Decision**: A Coach's weekly schedule stores local wall-clock time (`start_time time`, `end_time time`) plus an IANA zone identifier (`America/New_York`, etc.) — never a fixed UTC offset. Slot generation (`availability.ts`) computes each generated slot's actual UTC instant at generation time, using the zone's rules for that specific date, so "9am-5pm" for a Coach always means 9am-5pm in their zone even across a DST transition, per FR-041/SC-008.

**Rationale**: Storing a fixed UTC offset (e.g. "UTC-5") would silently produce a wrong wall-clock time the moment a DST transition crosses the generation window, since the offset for "9am Eastern" is different in January than in July. Storing the IANA zone name and resolving the offset per-generated-date is the only representation that's correct year-round without a recurring manual correction — the same reasoning the source spec calls out explicitly ("handle daylight saving correctly," "test DST transitions").

**Alternatives considered**: Pre-generating all future slots as fixed UTC timestamps once, on schedule save, was considered (simpler generation-time logic). Rejected because it can't self-correct if a DST rule changes (rare but real, e.g. a jurisdiction changing its DST policy) and because it front-loads a potentially huge number of rows for a far booking horizon; generating slots lazily/incrementally as the booking horizon rolls forward (a scheduled job extending the generated window, same renewal-cron pattern as #3) avoids both problems.

## 5. Credits adapter: interface now, placeholder-over-Core-snapshot implementation now, live Core write is a documented external dependency

**Correction**: the first version of this decision assumed a `DjangoCreditsAdapter` could make live debit/refund calls against Core's API at launch. Checking prior spec history (per the user's explicit request) found that's false: 008-staff-credit-watch's own `plan.md` states outright that "live write access to Core doesn't exist yet," and 008 itself only records credit changes as `'placeholder'`-status rows in a Academy-owned Supabase table (`credit_adjustments`), with a `'synced'` status reserved for a future cutover that has never happened. 008's own bulk-read endpoint (`POST /pull_credit_watch/`) is *also* still unshipped and blocks that feature today. There is no live write path to build against.

**Decision**: `src/lib/booking/credits.ts` defines a `CreditsAdapter` interface (`checkCredit`, `debitCredit`, `refundCredit`), with one implementation (`PlaceholderCreditsAdapter`) that mirrors 008's exact established pattern rather than inventing a new one: `checkCredit` reads the Student's balance from the existing, already-working single-student `fetchSnapshot()` endpoint (`src/lib/core-api.ts`) and overlays it with this feature's own not-yet-synced placeholder adjustments (008's "effective balance" technique) to get a real-time-accurate number even though Core's own number is stale between snapshots; `debitCredit`/`refundCredit` write a `credit_transactions` row with `status='placeholder'` (data-model.md), enforced immediately for future `checkCredit` calls regardless of whether Core has ever seen it. **Implementation correction**: the wallet key is Core's own numeric `lesson_type_id` (`SnapshotWallet.lesson_type_id`, `src/lib/types.ts`), not a Academy category string as first drafted — a Academy category is a grouping over several real Core lesson types, not a lesson type itself, so each credit-gated Booking Event stores which specific `creditLessonTypeId` it draws against (`contracts/payload-collections.md`). `UNIQUE (booking_id, transaction_type)` makes every debit/refund idempotent regardless of retry (FR-024/025, SC-003), identical in shape to 008's `credit_adjustments` idempotency approach.

A **Core write-endpoint handoff contract** (`contracts/core-credits-write-api.md`, mirroring 008's `contracts/core-credit-watch-api.md` format exactly) documents what Core would need to expose for a future `LiveCoreCreditsAdapter` to sync these placeholder rows to `'synced'` — this is an explicit external dependency for the *ledger of record* to become Core itself, not for this feature's own credit *enforcement*, which is real and live from day one against Academy's own placeholder ledger.

**Rationale**: The user's clarification during `/speckit-specify` ("connect at launch") was answered before this constraint was known; re-verified against actual prior-feature history rather than silently building against a Core write API that doesn't exist. The adapter interface is still worth keeping even with only a placeholder implementation at launch — the source spec explicitly calls for "Django adapter now, Academy platform adapter later," and 008 already proves this exact placeholder-then-sync shape works operationally for this codebase's relationship with Core.

**Alternatives considered**: Blocking this entire feature until Core ships a write endpoint (mirroring how 008 is blocked on its read endpoint) was considered. Rejected — unlike 008's renewal-coverage logic (which has no possible client-side substitute), credit enforcement has a proven, already-shipped substitute (008's placeholder-adjustment pattern), so there's no reason to block Live Coaching's launch on external work outside this team's control when a safe, precedented alternative already exists.

**Alternatives considered**: Calling Django directly from `bookings.ts` with no adapter abstraction was considered as the simpler option for a single-implementation launch. Rejected because the future-adapter requirement is explicit and stated as required in the source spec, not speculative — the interface costs one extra file and a handful of type definitions now, versus a real refactor later when the Academy-platform credit system exists.

## 6. Workshop waitlist: time-boxed hold, promoted on cancellation

**Decision**: `workshop_waitlist_entries(workshop_id, student_id, position, offered_at, expires_at)`. When a seat frees up (a confirmed booking is cancelled), the earliest waitlisted Student is offered the seat with a fixed hold window (e.g. 2 hours — exact value a config constant, not hardcoded inline) during which only they can claim it; if the hold expires unclaimed, the next Student in line is offered it, and so on. Claiming a hold uses the same atomic-capacity-claim guarded-UPDATE pattern 013 already established for group slots (013 research.md #3), so a claim race between "the hold's Student claims it" and "the hold expires and the next Student is offered" can never double-book the seat.

**Rationale**: An unbounded hold (first-offered, first-claimed, no expiry) risks a seat sitting unclaimed indefinitely if the offered Student never responds, defeating the purpose of a waitlist. A time-boxed hold with automatic promotion (Edge Cases: "a Student on a workshop waitlist never responds") keeps the seat moving without requiring an Admin to intervene manually.

**Alternatives considered**: Auto-booking the next waitlisted Student immediately with no hold/response window was considered (simpler, no expiry job needed). Rejected — it removes the Student's chance to decline (their availability may have changed since joining the waitlist), which is a worse experience than Calendly-style waitlist behavior generally offers.

## 7. Session records: denormalized snapshot for immutable history

**Decision**: `session_records` (created when a booking's session actually starts/completes, not just when it's booked) stores denormalized `coach_name`, `event_type_title`, and `session_category` values captured at record-creation time, in addition to the live foreign-key-style references (`coach_id`, `event_type_id`). Historical queries (Story 5's export/API) read the denormalized fields, never a live join back to `BookingEvents`/staff profiles.

**Rationale**: FR-038 requires history to remain unchanged if a coach, student, or event type is later edited or deleted — a live join would silently rewrite a payroll export's "coach name" column if that Coach's name changes, or break entirely if the event type is deleted. Denormalizing the handful of display fields actually needed for export/reporting at record-creation time is the standard technique for "this number must never retroactively change," and costs only a few extra text columns.

**Alternatives considered**: Soft-deleting (never hard-deleting) coaches/event types was considered as an alternative way to keep joins valid forever. Rejected as insufficient on its own — it solves "the row still exists" but not "the row's fields didn't change" (a Coach's display name being corrected doesn't need to rewrite last year's payroll export), so denormalization is needed regardless of delete strategy.

## 8. Reusing Ask a Coach's `audit_log`, `api_keys`, `webhook_subscriptions`/`webhook_deliveries` tables

**Decision**: These four tables, created for the Ask a Coach feature (specs/016) in this same Supabase project, are reused as-is for Live Coaching rather than creating booking-specific duplicates. `src/lib/booking/audit.ts`/`api-keys.ts`/`webhooks.ts` are thin academy-platform-side wrapper modules (mirroring Ask a Coach's own `writeAuditLog`/`verifyApiKeyFromRequest`/`deliverWebhookEvent` shapes) writing to/reading from the identical physical tables — not a cross-app code import (no `packages/` extraction, consistent with 013/016's established no-cross-app-import precedent), just two features' own small wrapper code pointed at one shared schema.

**Rationale**: `audit_log`'s columns (`actor_staff_id`, `action`, `target_type`, `target_id`, `diff`) are already fully generic — nothing about them is Ask-a-Coach-specific. Same for `api_keys` (`name`, `hashed_key`, `is_read_only`, `created_by_staff_id`, `revoked_at`, `last_used_at`) and `webhook_subscriptions`/`webhook_deliveries` (`url`, `events text[]`, `signing_secret` / `event_type`, `payload`, `status`, retry fields) — `events` being a free-form array already supports adding `booking.created`/`booking.rescheduled`/etc. alongside Ask a Coach's own event names with zero schema change. Creating a second, booking-specific copy of these tables would mean two places to check for "who changed what" and two places to manage API keys, which is strictly worse for the Admin who manages both features' staff.

**Alternatives considered**: Fully separate booking-specific tables (mirroring 013's own precedent of "each feature gets its own tables") were considered, for schema independence between the two features. Rejected specifically for these four tables because they're not really feature-specific data (unlike `coach_submissions` or `bookings`, which genuinely differ in shape) — they're infrastructure/administrative tables whose whole purpose is a single unified view across everything staff do, and splitting that view in two would undermine the audit log's own reason for existing.

## 9. Session export: `exceljs` for XLSX, native string-building for CSV

**Decision**: CSV export (FR-036) is generated with plain string-joining/escaping (no dependency needed — CSV has no complex format to fight). XLSX export uses `exceljs`, a maintained, widely-used library with no known license concerns, streamed directly to the response rather than buffered fully in memory for large date ranges.

**Rationale**: Adding a dependency for CSV would be needless — it's a trivial format. XLSX genuinely needs a real library (it's a zipped XML format); `exceljs` is the standard choice for Node/TypeScript and has no native-binary build step (unlike some faster alternatives), keeping deployment simple.

## 10. ICS feeds: `ical-generator`, token-based per-student URLs

**Decision**: The public workshop calendar's ICS feed (FR-013) is generated from currently-published workshops on each request (no caching needed at expected traffic levels) using `ical-generator`. A Student's own-bookings ICS feed is served at a URL containing an unguessable per-student token (not their raw student id), so the feed link can be safely handed to any calendar app without exposing an enumerable identifier.

**Rationale**: `ical-generator` is a small, well-maintained library producing spec-compliant ICS output with no other dependencies. Token-based (not session-authenticated) student feed URLs are necessary because calendar apps fetch subscription URLs without carrying the Student's Academy login session — the same reasoning any "subscribe to your calendar" feature across the industry uses.

## 11. Cross-category availability conflict prevention

**Decision**: `coach_availability_schedules` includes a `category` column (one-on-one / group / workshop); saving or editing a schedule runs a server-side overlap check against that Coach's *other* schedules in different categories for the same day-of-week/time-range, using half-open interval comparison (`new.start < existing.end AND new.end > existing.start`). An overlap blocks the save with a clear error identifying the conflicting schedule (FR-004), rather than allowing it and producing confusing double-offered slots later.

**Rationale**: FR-004 requires this be prevented, not just detected after the fact — catching it at save time (with a specific, actionable error) is far better UX than allowing an invalid schedule and surfacing the conflict only when a Student tries to book (or worse, two Students book overlapping sessions for the same Coach).

## 12. Stable v1 scheduling API + identity handoff

**Decision**: `/api/v1/booking/*` (contracts/api.md) is the only interface the booking UI itself calls internally (no page calls `src/lib/booking/*` Server Actions directly for anything the API also exposes) — mirroring Ask a Coach's existing `/api/v1/*` pattern and the source spec's explicit "the in-app Live Coaching tab and any web page use only these endpoints" requirement (FR-048). Identity handoff (FR-049) reuses the same signed-JWT pattern Ask a Coach already built for `HOST_JWT_SECRET`/host-identity tokens (`verifyHostIdentityToken`), reimplemented as its own small booking-scoped module rather than imported cross-app.

**Rationale**: Treating the API as the *only* caller (not an optional parallel surface next to direct Server Action calls) is what actually delivers "the engine can be swapped later" and "any future embed/in-app surface uses only these endpoints" — an API that exists but that the UI bypasses half the time isn't a real contract. Reusing Ask a Coach's already-proven JWT-identity-handoff shape avoids re-inventing a security-sensitive pattern that's already been designed and tested once this session.

**Alternatives considered**: Keeping the existing 013 Server Actions as the UI's primary interface and adding the `/api/v1/*` layer only for external/future callers was considered (less refactoring of working 013 code). Rejected — it would mean two divergent code paths for the same booking logic (Server Actions for the web UI, API routes for everyone else), which is exactly the "no caller talks to the underlying scheduling engine directly" problem FR-048 is written to prevent; the API routes call into `src/lib/booking/*` and the existing Server Actions become thin wrappers wired to those same lib functions instead of duplicating logic.
